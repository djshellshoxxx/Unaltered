Compiled 2026-10-09 from web searches and primary-page fetches. Each finding states how well it is supported. **Treat anything marked "unverified" as a lead, not a fact**, and confirm it in the milestone noted.

## 1. How OpenTimestamps works (from secondary + primary sources)

- A client hashes the file locally and submits the hash to public calendar servers, which aggregate many hashes into a Merkle tree and anchor the root in a Bitcoin transaction. The client first gets an incomplete ("pending") proof and later upgrades it to a full proof reaching the block header. Verification needs the original file, the `.ots`, and Bitcoin block data, ideally from the verifier's own node. Source: [Wikipedia: OpenTimestamps](https://en.wikipedia.org/wiki/OpenTimestamps); IETF draft citing the format: [draft-fassbender-scitt-time-anchor-02](https://www.ietf.org/archive/id/draft-fassbender-scitt-time-anchor-02.xml).
- **Primary check (fetched):** the official JS repo's README describes `stamp`, `upgrade`, `verify` commands, says verification "tries a local Bitcoin node first and falls back to block explorers", and that explorer verification "is convenient but not as secure as asking a local node". Lists calendars `alice.btc.calendar.opentimestamps.org`, `bob.btc.calendar.opentimestamps.org`, `finney.calendar.eternitywall.com` in example output. [javascript-opentimestamps](https://github.com/opentimestamps/javascript-opentimestamps)
- **Primary check (fetched):** the official Python repo's README does not document the file format, nor point to a spec or test vectors; it separates consensus-critical `opentimestamps.core.*` from other modules. [python-opentimestamps](https://github.com/opentimestamps/python-opentimestamps)
- **Unverified:** the Bitcoin attestation tag constant quoted in the IETF draft; whether the reference client adds a privacy nonce when stamping; CORS behaviour of calendars. All to be confirmed from source in M0.

## 2. Reusable audited components

- **`@noble/hashes`** (fetched README): 0 dependencies; independently audited by Cure53 at v1.0.0 in Jan 2022, scope "everything, besides blake3, sha3-addons, sha1 and argon2"; signed commits; releases via token-less CI and Trusted Publishing; supports incremental SHA-256 (`sha256.create().update(...).digest()`); the README mentions AI-assisted self-audits since Apr 2026. [noble-hashes](https://github.com/paulmillr/noble-hashes), [Cure53 hashing-libs report](https://cure53.de/pentest-report_hashing-libs.pdf), [noble overview](https://paulmillr.com/noble/). *Note: I read the README, not the full Cure53 PDF.*
- **libsodium** was reviewed in 2017 (v1.0.12/1.0.13) with no critical flaws found: [PIA audit results](https://www.privateinternetaccess.com/blog/2017/08/libsodium-audit-results/). Not needed for v0.1 (we hold no keys) but listed as the reference for any later key handling.
- **Gap found:** no published independent audit located for any OpenTimestamps JavaScript client. Several third-party npm forks self-describe as hardened ("zero dependency", "fail closed"); unverified. See [socket.dev listing](https://socket.dev/npm/package/@otskit/core) (self-reported).

## 4. Browser hardening references

- **Subresource Integrity:** `integrity` attribute carries a base64 SHA-256/384/512 digest; browser blocks on mismatch; pair with `crossorigin="anonymous"`; pin exact URLs (never `@latest`); regenerate hashes per change. [KeyCDN: SRI](https://keycdn.com/support/subresource-integrity), [InventiveHQ: implementing SRI](https://inventivehq.com/blog/how-to-implement-sri-on-website)
- **CSP vs SRI:** different jobs; CSP restricts sources, SRI verifies content. CSP via `<meta>` cannot set `frame-ancestors`, `report-uri`, or `sandbox`, so use headers where possible. (From search summaries; verify against the CSP spec during M2.)
- **Trusted Types:** the MDN fetch failed (network), and the search returned nothing usable. **Unverified** for browser support and Tor Browser behaviour; Q7, M2. Treat as defence in depth only.
