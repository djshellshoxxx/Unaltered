## Executive summary

This pass reviewed the application as a whole rather than concentrating on one subsystem. **No additional confirmed exploitable vulnerability was established.** The principal security design is coherent: browser and CLI entry points share core logic; file bytes are processed locally; the network client is centralized and host-restricted; OpenTimestamps proofs are parsed and replayed before verification; dynamic UI values are rendered as text; and the build applies restrictive CSP/SRI controls.

The strongest remaining risks are not a newly demonstrated parser or network bypass. They are the previously reported project-generator symlink issue, credential handling, broad write scope in the cloud coding workflow, and resource exhaustion from unbounded concurrent file hashing. The application also remains trust-on-first-use when delivered as a website: a compromised delivered bundle can bypass protections implemented inside that same bundle.

No application code was changed. This report is an audit record, not a security certification.

## 1. Architecture and attack surface

### Entry points and shared core

- Browser entry: `src/main.ts` mounts the Stamp, Verify, About, Settings and archival tools views.
- CLI entry: `src/cli/main.ts` dispatches to `src/cli/run.ts`.
- Both entry points use shared hashing, OpenTimestamps parsing/verification, metadata cleaning and report-generation modules.
- The browser build bundles `src/main.ts`; the Node CLI is built separately from `src/cli/main.ts`.
- Third-party dependencies in `package.json` are exact-pinned; the runtime dependencies are `@noble/hashes` and `jsqr`.

**Assessment:** Separation between UI/CLI orchestration and shared core logic reduces duplicated security-sensitive implementations. The two entry points still have different environmental assumptions (browser storage, browser file APIs and workers versus Node filesystem and CLI output); both require dedicated tests.

### Primary trust boundaries

1. **Untrusted file bytes → local decoders/cleaners/hashers.** File names and contents are attacker-controlled. File format detection uses magic bytes; format cleaners use bounded parsing and fail-closed outcomes; hashing checks declared byte lengths and supports cancellation.
2. **Untrusted receipt bytes → OTS parser and proof replay.** Receipts are attacker-controlled. Parser limits, structural validation and replay are applied before proof results are accepted.
3. **Application → external calendars/explorers.** Only `src/core/net/fetch.ts` calls `fetch()`. Production destinations are constrained by the central host allowlist and generated CSP.
4. **Untrusted server responses → proof/header parsers.** HTTP status, response byte limits, header size/hash and OTS structure are checked locally.
5. **Application state → browser persistence and downloads.** Receipt-list storage is opt-in; dynamic values are inserted through DOM text APIs; export formats are bounded and labelled as unverified where appropriate.
6. **Source tree → build artifacts → user.** Build-time CSP/SRI, pinned dependencies/actions and manual unsigned draft release preparation reduce risk, but cannot alone establish the integrity of the final hosting account or user's downloaded copy.
7. **AI-assisted workflow → repository write operations.** The development job has read-only repository permissions, but a later publisher job has write permissions and applies a patch generated by the agent. Its path guard is therefore a meaningful security boundary and must be narrow and independently enforced.

## 2. File privacy and processing — no new finding

**Reviewed:** `src/ui/views/stamp.ts`, `src/core/strip/*`, `src/core/hash/*`, `src/core/archive/*`, `src/ui/download.ts`.

- The stamp flow detects the file type, optionally cleans supported image/audio formats, hashes the selected target, and requires the cleaned output to be downloaded before stamping when cleaning occurred.
- The hash is computed locally. Calendar submission sends a blinded commitment derived from the digest and a fresh 16-byte nonce; it does not send the original file bytes or filename.
- Metadata cleaners are explicit format-specific transformations. Unsupported types are not silently described as cleaned.
- Hashing uses incremental SHA-256 and bounded chunk reads; the worker path and main-thread fallback share the same hashing implementation.
- QR archival image parsing bounds input bytes and dimensions before raster processing, then decodes in a disposable worker with timeout/abort handling. Reassembled proof data is bounded and checked against its digest and proof identifier.
- Download object URLs are tracked and revoked when the owning UI state is replaced or removed.

**Assessment:** No file-content network exfiltration path was found in the reviewed stamp flow. The privacy claim must remain carefully scoped: calendars receive blinded commitments and can still observe IP address, timing and use of the service; metadata stripping does not erase identifying information encoded in image/audio content or guarantee anonymization. A compromised delivered application can of course alter these behaviours.

**Carried-forward availability risk:** RT-04 and RT-05 remain relevant. QR decoding and multi-file hashing have resource limits in parts of the pipeline, but the UI can still start too many independent file-hash tasks at once. See prior audit reports.

## 3. Network boundary and service trust — no new finding

**Reviewed:** `src/core/net/allowlist.ts`, `capability.ts`, `fetch.ts`, `src/core/ots/calendar.ts`, `bitcoin.ts`, `trusted-header.ts`.

- `netFetch` is the sole production fetch wrapper. It validates HTTPS, host, credentials and port; disallows redirects; omits credentials and referrer; uses no-store; applies timeout/cancellation and response-size limits.
- The build derives `connect-src` from the same endpoint allowlist, reducing drift between application policy and CSP.
- Calendar URLs in pending attestations are not treated as arbitrary destinations: upgrade only contacts normalized pending bases selected in the configured calendar list, and the transport layer independently checks the host allowlist.
- Explorer responses are not trusted as raw proof data. The app parses the 80-byte header and locally verifies that its double-SHA256 matches the explorer's claimed block hash.
- Quorum counting deduplicates sources by host identity and requires at least two matching independent configured sources.
- Offline trusted-header verification explicitly treats the height-to-hash mapping and chain membership as user-supplied trust inputs; it does not claim to validate Bitcoin consensus.

**Residual trust-model limitation (not a new bug):** Two explorers agreeing on a locally hash-checked header is not equivalent to independently validating proof of work, difficulty, cumulative chainwork or best-chain membership. The product's trust language and own-node/reference-client guidance must remain explicit.

## 4. Proof correctness and result semantics — no new finding

**Reviewed:** `src/core/ots/codec.ts`, `ops.ts`, `verify.ts`, `calendar.ts`, `bitcoin.ts`, `src/core/reports/verification.ts`.

- Receipt parsing applies explicit input, depth, node, operation and attestation limits.
- Verification compares the supplied file digest with the receipt digest before any confirmed result.
- The proof is reconstructed/replayed from the file digest; the stored in-memory commitments are not accepted as authoritative.
- A Bitcoin attestation is only reported VERIFIED when the locally parsed header's Merkle root matches the replayed commitment and the configured explorer quorum agrees on the header.
- Pending receipts remain PENDING; an unreadable calendar response is not upgraded to confirmation.
- Upgrade merges are validated by serializing the complete resulting proof, preserving the original proof structure and rejecting malformed results.
- Report JSON explicitly distinguishes verification state and includes warnings; inspection/evidence export paths do not misrepresent an unverified receipt as a verified one.

**Assessment:** No false-VERIFIED shortcut or pending-to-confirmed promotion was established in the reviewed call paths. The explorer quorum's residual trust limitation above remains.

## 5. UI, persistence and browser security — no new finding

**Reviewed:** `src/main.ts`, `src/ui/dom.ts`, `router.ts`, `state.ts`, `store.ts`, `download.ts`, `src/index.html`.

- UI text is built with DOM APIs and text nodes; the shared DOM helper explicitly avoids `innerHTML`.
- The share link carries only the fingerprint in the URL fragment, which browsers do not send in HTTP requests. Invalid/conflicting fingerprints are discarded.
- The local receipt list is opt-in and stores digest, timestamp and user-entered label, not file bytes.
- Stored records are treated as untrusted, shape-checked and bounded when loaded.
- Download object URLs are scoped and revoked to limit stale references.
- The app refuses to operate inside a frame after startup. The meta CSP cannot provide `frame-ancestors`, so this is a script-enforced fallback rather than an HTTP-header frame policy.

**Residual risks:** Browser same-origin compromise or malicious delivered code can read localStorage and alter UI results. The current DOM/text approach lowers DOM-XSS exposure but does not protect against a compromised bundle or malicious browser extension. A static-host deployment cannot reliably set every HTTP response header; the generated meta CSP and SRI controls should not be described as equivalent to a hardened server-header policy.

## 6. Build, dependency and CI supply chain — no new finding

**Reviewed:** `package.json`, `scripts/build.mjs`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `.github/workflows/pages-deployment.yml`.

- Dependencies and GitHub Actions used in the reviewed workflows are pinned; CI installs npm dependencies with lifecycle scripts disabled and checks npm signatures.
- Build output is bundled locally, with no runtime CDN dependency. Multi-file assets use SRI; the single-file build uses CSP hashes. Worker source is bundled into the page code rather than loaded from an unpinned external worker URL.
- CSP is restrictive: default deny, explicit script/style policies, allowlisted network connections, blob workers, no objects/base/forms, and Trusted Types enforcement.
- Release workflow is manually dispatched against an existing exact version tag and creates an unsigned draft only. It rechecks the remote tag and checks downloaded artifacts against checksums; signing and publication remain separate maintainer steps.
- Pages deployment is an inactive template and requires explicit authorization inputs and a reviewed commit in the workflow.

**Assessment:** No direct unpinned runtime script, automatic signing or automatic final release path was identified in these files. YAML and build-source inspection cannot establish repository rulesets, environment reviewers, account security, signing-key custody or what is actually served by a hosting provider.

## 7. AI-assisted repository workflow — prior finding remains

**File:** `.github/workflows/unaltered-codex-cloud.yml`

- The development job checks out main with persisted credentials disabled and has read-only repository permissions while the agent works.
- A subsequent publisher job has contents, pull-request and Actions write permissions; it applies the generated patch as data, opens a PR and dispatches CI.
- The prompt excludes security-sensitive policy files, but the path validation permits broad `src/*` and `scripts/*` paths. Its denylist does not block every sensitive file under those directories, including network policy, proof verification, and OPSEC code.
- The workflow is PR-based and does not automatically merge or release the patch.

**Assessment:** This remains **RT-03 (Medium)**. The prompt is guidance, not a security boundary. Since the publisher applies an agent-produced patch in a job with write permissions, a compromised or misdirected agent could modify sensitive application trust code while satisfying the current broad path check. Enforce a narrow positive path allowlist, or explicitly protect trust-critical files and require designated maintainer review for changes to network, proof, cryptography, build, release and OPSEC controls.

## 9. Prioritized remediation

1. **RT-01:** Change starter copying to reject symlinks or prove every resolved source remains beneath the trusted starter root. Add fixtures for file and directory symlinks, including links that escape via parent traversal.
2. **RT-03:** Make the cloud workflow's path gate a positive allowlist. Protect network allowlists, transport, proof parser/replay, hashing, cryptographic code, build/release, and OPSEC controls. Require explicit human review for those paths.
3. **RT-02:** Accept secrets through a safer input channel, never argv; create secret files with restrictive permissions from creation and avoid logging them.
4. **RT-05:** Put file hashing behind a bounded queue, enforce a maximum batch size at the core API as well as the UI, and test cancellation/worker cleanup under load.
5. **RT-04:** Measure peak memory in supported browsers at maximum input dimensions and during cancellation; lower limits if the worst-case peak is unsuitable for ordinary devices.
6. **Trust assurance:** Keep the own-node/reference-client verification path prominent and describe explorer quorum as a trust model, not consensus validation.
